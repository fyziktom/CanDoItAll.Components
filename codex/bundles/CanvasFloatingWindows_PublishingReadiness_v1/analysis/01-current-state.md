## Main Findings

- F01 High: CanvasLib is a real publishing unit but lacks a dedicated package/API approval and test foundation comparable to the standard package wave. Owner: SB01, SB03, SB09.
- F02 High: Floating-window behavior is split across `OverlayWindow`, `OverlayWindowState`, `CanvasFloatingWindow`, and `CanvasWorkbenchWindowState`. The wrapper relationship is sensible, but ownership and equivalence rules need explicit tests and docs. Owner: SB02, SB07.
- F03 High: Canvas runtime JavaScript has a generated asset manifest and good service/runtime split, but several runtime modules are large enough to need a module map, source assertions, node syntax checks, asset-order verification, and no-regression browser proof before refactor. Owner: SB04.
- F04 High: True validation must cover workbench interactions, not only route rendering. Selection, context menu, quick create, drag/drop, keyboard shortcuts, zoom, fit/focus, minimap, diagnostics, accessibility mirror, and image export need observable proof. Owner: SB05.
- F05 High: Calendar is part of CanvasLib but has a separate JS controller/render stack and callback surface. It needs explicit contract, timezone/date, selection, CRUD, playlist, export, and visual proof. Owner: SB06.
- F06 Medium: `src/CanDoItAll.Components.CanvasLib/README.md` says package version `0.1.0`, while `CanDoItAll.Components.CanvasLib.csproj` sets `PackageVersion` to `0.1.1`. Owner: SB09.
- F07 Medium: Canvas asset include components are generated by `tools/canvaslib/build-assets.cjs`, and `npm run canvaslib:verify-assets` exists. The bundle should require generated-asset synchronization proof instead of hand edits. Owner: SB04, SB09.
- F08 Medium: Sandbox coverage exists for `/groups/canvas`, `/groups/canvas/benchmark`, and `/groups/overlays`, with scenarios for happy, dense, empty, disabled, loading, and long text, but Canvas has not yet gone through the full publishing visual matrix. Owner: SB08.
- F09 Medium: `CanvasBenchmark` is explicitly scoped as draw-cost evidence only and says it does not claim feature parity for overlays, accessibility, export, or editor workflows. This bundle must not convert it into a renderer migration. Owner: SB08, SB10.
- F10 Medium: The component MCP transport closed during preparation. Implementation should retry MCP usage before layout refactors and record fallback evidence if unavailable. Owner: SB01 and each UI subbundle.

## Implementation-Relevant Observations

- `CanvasFloatingWindow.razor` is a typed wrapper around `OverlayWindow` with `InteropApiRoot="CanDoItAll.canvasFloatingWindow"`, default container `.cw-stage-surface`, and safe top `.cw-toolbar`.
- `OverlayWindow.razor` owns generic floating-window header/body/minimized rendering, JS interop create/update/dispose, action labels, geometry payload, and state publishing.
- `CanvasWorkbenchWindowState` and `OverlayWindowState` both normalize positive numeric geometry to two decimals and drop non-positive values. Tests should prove these stay equivalent through roundtrip conversions.
- `CanvasWorkbench.razor` owns high-value public behavior: selection, move, context action, create action, node edit, node open, state change, clipboard, help/settings overlays, zoom, maximize, minimap, diagnostics, fit/focus, selected-node APIs, state export, and image capture.
- `CanvasLibBodyAssets.razor` includes OverlayLib runtime before Canvas services/runtime files. This order is generated and should become a verifier-backed contract.
- `StandardPublishingApprovalTests` currently snapshots standard projects and includes OverlayLib, but not CanvasLib. Canvas publishing readiness should add Canvas-specific approval coverage rather than overloading the completed standard scope.
